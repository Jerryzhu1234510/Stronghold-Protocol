## 已确认的问题与修复

1. 渲染器此前忽略间隔超过 250 ms 的帧：FPS 统计排除它们，自动降载也直接返回。持续低于 4 FPS 时反而无法降低特效及骨骼动画负担。现在长帧仍参与判断，每帧对降载计时最多贡献 250 ms；一次后台返回/GC 长帧不会直接切换档位。恢复采用迟滞，避免画质频繁跳变。
2. 浏览器追帧原本只有 tick 数上限（240，初始追赶 600），没有实际耗时上限。现在可见帧的模拟预算为 12 ms，观战时自身权威场地与观战副本共享；后台泵预算为 32 ms，初始重连追赶也分段让出主线程。

预算检查发生在完整 tick 之间。单个 tick 不可切断，因此一次很慢的 tick 或事件/绘制工作仍可能超过 12 ms；这不是整帧时间保证。未处理 tick 留在原来的场地时钟上，后续继续计算，没有跳 tick、降低模拟速度、简化伤害或修改结算。持续计算能力不足的设备仍需要进一步优化，不能靠无限减小切片预算解决。

未修改手机镜头、首领血量、属性、掉落、难度或 5–8 人玩法规则。原来按素材内容哈希缓存的机制继续保留。

## 后续优化次序

先以 r09 的真实 5–8 人首领对局反馈核验效果，并把帧率、模拟耗时、主线程停顿和房间人数/阶段对应起来。不要据本次局部修复承诺所有卡顿已消失。

若模拟与渲染仍争抢主线程，可将确定性战斗移入 Web Worker，保留相同模拟逻辑，并验证消息顺序、池同步、接管、重连和结算。Worker 提高主线程可响应性，不保证单个计算本身变快：[MDN Web Workers](https://developer.mozilla.org/en-US/docs/Web/API/Web_Workers_API)。

若 GPU 压力为主，进一步按负载减少非必要粒子、伤害数字刷新、阴影或渲染分辨率，不改变格子坐标/点击映射。若服务器阻塞为主，检查托管模拟、机器人预演和公共状态构建的耗时，再考虑按房间分配多个工作进程；监测总内存，避免重复全量数据/缓存。若下载流量与对局 RTT 明确相关，再考虑静态素材外置/CDN。浏览器素材缓存减少重复下载，并不直接省去战斗计算和绘制：[MDN 缓存指南](https://developer.mozilla.org/en-US/docs/Web/Progressive_web_apps/Guides/Caching)。
